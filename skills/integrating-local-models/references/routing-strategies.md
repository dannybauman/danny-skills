# Routing Strategies for the Two-Wall Ceiling

When local does the *light* steps fine but wedges on a *heavy* one (the 64K-vs-128K squeeze under memory discipline), "all local or all cloud" is the wrong granularity — it pays cloud for steps a local model would do at $0. Two strategies, both better than forcing the whole run to cloud because one step is heavy:

1. **Per-step engine routing.** Let each step pick its engine (harness · model) before the run, with a smart default: heavy/unbounded steps (web research) → big-context cloud; bounded file-in/file-out steps (SEO, draft, certify) → local. Carry a per-step backend map through dispatch (the seam usually already reads a backend per call). **Readiness becomes per-step, not global** — a step routed to the cloud agent needs its session capability (e.g. a subscription verify) surfaced *before* the run, not as a mid-dispatch failure; and *verifying* a capability must grant it session-wide WITHOUT also flipping the global default (else the carve-out silently escalates the whole run). In a project that routes steps between engines, this lands as a step-routing resolver plus an "unready backends for this run" preflight.
2. **Step decomposition.** The deeper fix for the heavy step itself: the wall is one loop accumulating every fetch into a growing context. Subdivide — fetch+summarize one source per bounded sub-invocation, discard the raw page, then synthesize the summaries — so each invocation stays small and local stays viable end-to-end.

## Model picks (verified on a 16GB M1 Pro, opencode 1.17.4)

- `qwen3.5-9b` (Qwen3.5, in LM Studio at 64K ctx) **PASSES** — it wrote a file and landed a commit. The Qwen3/Qwen3.5 family has the most reliable native tool-calling at this size. **`qwen2.5-coder:7b` FAILS** despite being the "canonical" local coder and despite `tools: true` — it emits tool-calls as a JSON text block instead of executing them, at 4K *and* 32K context (`probe.sh` also flags it rung-3 ✗). The smallest dedicated `qwen3-coder` is 30B (too big for 16GB) — reach for `qwen3:8b`/`qwen3.5-9b` instead.
- **Gemma 4 12B is now a real contender (the old "Gemma: no" was Gemma 3 / medgemma).** Gemma 4 (June 2026, ~10GB, fits 16GB) was trained on tool-use data — 86.4% on τ2-bench agentic tool use vs Gemma 3 27B's 6.6%, a discontinuous jump — and has **no think-token overhead**. Needs Ollama ≥ v0.20.2 for the tool-call parse fix. Worth probing as a qwen3.5 alternative; don't trust a stale "weaker tool-calling" label. Still gate it on `probe-opencode.sh` — measured, not assumed.
- **Server choice changes tool-call fidelity, not just speed.** Independent reports converge: **Ollama maps tool-calls more faithfully to the OpenAI spec than LM Studio**, whose two-tier native/`[TOOL_REQUEST]`-fallback can lose signal for less-common models. If a model emits-as-text on LM Studio, retry the same model on Ollama before concluding it can't tool-call. (Trade-off: LM Studio/MLX decode is faster for short context — see the prefill wall in `gotchas.md`.)
