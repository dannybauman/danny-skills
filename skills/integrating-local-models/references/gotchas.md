# Gotchas That Cost Hours

- **The context trap (the big one).** opencode's *base* system+tools prompt is ~23K tokens (`n_keep ≈ 22803`) — but a **real agentic step** (step template + injected source/context) is bigger: a real app's "express" run measured **~36K** (`n_keep 35714`), and an **extract over a full 36-min transcript measured ~47K** (`n_keep 46959`). So the trivial emit-probe under-counts badly. **64K (65536) is the FLOOR for full-source agentic steps, not just a "safe default":** at 48K a ~47K-token prompt leaves only ~2K for output and **overflows mid-generation** even when the prompt itself fits. 32K passes a toy probe yet overflows on real work; 48K survives the prompt but not the output. Load **≥ 64K** for any step that injects a real source. The two runtimes fail *differently*:
  - **LM Studio errors loudly** on overflow (`n_keep ... >= n_ctx: 8192`). Its JIT auto-load uses the model's *default* context (often 8K) → this error. Pre-load big: `lms load <model> --context-length 65536` (or set the model default in the UI).
  - **Ollama silently truncates** to its 4K default — no error. The model never sees the front of the prompt where the tool-use instructions live, so it falls back to emitting tool-calls-as-text. Looks like a capability failure; is actually config. Fix: a real Modelfile tag — `FROM <model>` + `PARAMETER num_ctx 65536`, then `ollama create <m>-64k -f Modelfile`. (opencode's catalog id `<m>:7b-32k` is NOT a real ollama tag — opencode passes it literally and ollama 404s.)
  - Consequence: a model that passes the small-prompt `probe.sh` can still fail in opencode purely from truncation. Always confirm with `probe-opencode.sh`.
- **`opencode models` is a stale CATALOG, not your installed list.** It lists models you don't have and omits ones you do; an unregistered id throws `ProviderModelNotFoundError`. Register the model in `opencode.json` before referencing it.
- **The id-mismatch IS a real bug: the bare id "resolves" by JIT-loading a SEPARATE default-context instance.** `lms load qwen3.5-9b` registers/lists (`/v1/models`) the model **publisher-prefixed** as `qwen/qwen3.5-9b`, while your `opencode.json`/app requests the bare `qwen3.5-9b`. The bare id does *return a model* — but **not your pre-loaded one**: LM Studio's JIT layer spins up a **second instance under the bare id at the model's DEFAULT context (often 8192) and default parallel (4)**, silently ignoring the big-context instance you carefully loaded. Symptom (observed in a real run): `lms load … --context-length 65536` succeeded, yet the run overflowed at `n_ctx: 8192` — `lms ps` showed **TWO rows**: `qwen/qwen3.5-9b @ 65536 parallel-1` (yours) and `qwen3.5-9b @ 8192 parallel-4` (the JIT copy the request actually hit). Two compounding traps: (a) **`lms load --context-length N` is a no-op when an instance is already resident** (a GUI auto-load or a prior JIT) — it does NOT resize, so it stays at the default; (b) the loaded identifier ≠ the requested bare id, so JIT makes a new default one. **FIX: `lms unload --all` (clear stale/JIT instances) then `lms load <model> --context-length 65536 --parallel 1 --identifier <bare-id>`** — `--identifier` pins the served id to exactly what the client requests, so the request hits your instance instead of JIT-loading another. **Verify with `lms ps`: ONE row, the bare identifier, the context + parallel you asked for. Two rows = the bug.**
- **Auto-starting the host can transiently fail with EBADMACHO while LM Studio self-updates its own `lms` CLI.** If you spawn `lms server start` / `lms load` from a server (the operator-facing "start it for me" path), the spawn can fail with macOS **errno 88 = EBADMACHO** ("malformed Mach-O", surfaced by Node as the cryptic **"spawn Unknown system error -88"**) — or `ETXTBSY` — when LM Studio is mid-rewrite of its `lms` binary (it self-updates). The binary is fine once the write settles. **Retry the spawn with a short backoff** (transient, not a permanent failure) and map the raw errno to a human message ("the LM Studio CLI couldn't be launched — it may be updating; retry") rather than dead-ending the operator on `-88`. A logical failure (`ENOENT`, model-not-found) should NOT retry — only the transient exec errors (EBADMACHO/EBADARCH/EBADEXEC/ETXTBSY).
- **Memory discipline (16GB-class).** Loading two models at once, or LM Studio + Ollama both resident, thrashes swap and can lock the machine. One model at a time; unload between probes (`lms unload --all`; `ollama stop <model>`). A 9B at Q4 + 32K KV is ~7–8GB resident — fine alone, fatal alongside a second. **The KV cache scales with context: the same 9B at 128K pins ~12G wired and thrashes swap to ~11G on 16GB (near-lockup). So ~64K is the practical ceiling on 16GB** — which **wedges** any agentic step whose tool-loop context grows past it: a web-fetch-heavy step (e.g. "research") accumulates tool outputs, overflows 64K mid-loop, yet 128K won't fit RAM. Such steps need a big-context cloud agent (claude-code, ~200K) or >16GB; reserve local for the probe + lighter steps.
  - **That ceiling is not fixed — raise it with three levers before paying for cloud.** (1) **`--parallel 1`** — the cheapest, zero-quality-cost lever, and the one people miss: **LM Studio allocates the full `--context-length` *per* parallel slot**, so its default (often 4, via the GUI or a JIT auto-load) **quadruples** KV memory for sequences a single agentic run never uses. Measured on a 16GB M1: reloading `32K @ parallel-4` → `48K @ parallel-1` *lowered* resident RAM (system free rose ~20%→higher) AND gave the one run the full window — bigger context, less memory. Always `lms load <model> --context-length 49152 --parallel 1` for a single agentic runner. (2) **FlashAttention** (llama.cpp `-fa 1`; LM Studio → Advanced) — and (3) **KV-cache quantization** `--cache-type-k q8_0 --cache-type-v q8_0` (FA is a hard prerequisite), which roughly **halves** KV memory at negligible quality loss. q8_0 KV is the difference between fitting 64K and swapping on 16GB. Also drop the prompt itself: **`enable_thinking=false` on agentic steps** (see "Verify Before Claiming It Works" in SKILL.md) removes the reasoning budget you don't need for tool-calling.
  - **Preflight before you run — don't discover the wall by thrashing.** A *too-big source* dies the same way as a runaway loop: a 72K-char source → ~41K prompt tokens → ≥48K ctx → model + f16 KV overcommits 16GB → 15GB swap, zero output (measured). This is knowable from input size + RAM up front: `bash ${CLAUDE_SKILL_DIR}/scripts/ctx-budget.sh --source-chars 72000` → estimates required ctx, KV memory with/without q8_0, and a verdict (LOCAL-SAFE / LOCAL-WITH-LEVERS / ROUTE-TO-CLOUD). Route a ROUTE-TO-CLOUD step to claude-code instead of stalling the machine.
  - **Prefill, not just KV, is a wall on M1.** Big static prompts (a 23K base + injected source) spend real wall-time in *prompt processing* before the first token. LM Studio's MLX backend is fast at decode but its **prefill collapses at long context** (a documented 35B@8.5K: 51 tok/s decode but ~3 tok/s incl. prefill); **llama.cpp + FlashAttention wins total wall-time for large prompts.** If a local run sits in `PROCESSINGPROMPT` forever, suspect prefill + swap, not a hang. (Set Metal headroom too: `sudo sysctl iogpu.wired_limit_mb=12288` — reported the most impactful system-level setting.)
- **The runner starts itself; it does NOT start the model host — and "unreachable" fails *silently*.** A dispatch launches `opencode serve` on its own, but nothing brings up the LM Studio server (`:1234`) or *loads* the model — opencode assumes the host is already serving. From a cold start (LM Studio quit, or running but server stopped / no model loaded) the run doesn't error: it sits in a "thinking" / `GENERATING` state indefinitely while opencode waits on a dead endpoint (verified: 2+ min, zero output, no fast-fail in the UI — distinct from the *overflow* error, which surfaces loudly). **Preflight rung-1 reachability before every dispatch** — `curl -fsS http://localhost:1234/v1/models` — and if it's down, start + load the host yourself (`lms server start && lms load <model> --context-length 49152 --parallel 1`) rather than handing the operator a hang. A product that targets non-technical operators must do this preflight (and the start) for them, or at minimum fast-fail with "local model server not reachable at :1234."
- **Probe serially.** opencode boots a server per run and swaps `process.env` globally — never run two opencode probes (or app dispatches) concurrently.
- **Don't edit app source mid-run.** A dev server with HMR (Vite/Astro/Next) reloads the program on a source change, wiping in-memory run state — it kills the in-flight agentic run (its `/stream` then 404s) and orphans the spawned opencode subprocess (still `GENERATING`, detached). Persist run state if you want it to survive; otherwise leave source alone while a run is live.
- **Cancel hangs on an idle stream.** If your backend consumes the runner's SSE events with `for await` and only checks the abort flag at the top of the loop, a cancel while the model is idle won't be observed — the loop is blocked awaiting an event that never comes, so teardown never runs and the run is stuck "running" (and holds the serial mutex → next run deadlocks). Race the abort against `iterator.next()` (a "first settled" helper) so cancel breaks promptly and teardown fires. Tests with tight-loop fake runners won't catch this — only a real idle stream does.
